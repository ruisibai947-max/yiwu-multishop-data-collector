# 账号登录态冲突调研纪要

日期：2026-06-16

## 背景

现场验证发现，集中采集电脑在比特浏览器中登录 Temu 店铺账号后，员工自己电脑上的同一 Temu 账号可能被登出。该项目需要每天采集 Temu、TikTok Shop、SHEIN、聚水潭、京东等平台的多店铺经营数据。如果将约 200 个店铺账号集中登录到一台采集电脑，登录态互踢、验证码和人工重新登录会成为主要运维风险。

该问题的核心不是浏览器自动化本身，而是账号会话归属和平台风控策略：员工日常工作和采集程序在争抢同一账号登录态。

## 已确认现象

- Temu 主账号在集中采集电脑登录后，员工电脑上的同账号可能被顶下线。
- 员工重新登录后，集中采集电脑上的登录态可能在次日采集前失效。
- 如果每天需要处理几十到 200 个店铺账号，人工登录、短信验证码和异常恢复会放大为不可接受的运维成本。
- 后续顶号是否每次都需要验证码，取决于平台对设备、IP、指纹、登录频率和账号风险的判断，不能仅凭一次登录测试下结论。

## 需要验证的平台

| 平台 | 当前判断 | 待验证事项 |
|---|---|---|
| Temu | 已观察到主账号多设备互踢风险 | 首次新设备登录、已信任设备来回顶号、验证码频率、子账号可用性 |
| TikTok Shop | 需要验证 | 主账号/子账号/服务商授权的会话策略；API 和报表能否替代后台登录 |
| SHEIN | 需要验证 | 主账号授权要求、子账号日常操作、后台报表导出能力 |
| 聚水潭 | 需要验证 | 是否已有开放平台或客户现有 ERP 授权可直接取数 |
| 京东 | 需要验证 | 京东宙斯开放平台、商家后台导出和多设备登录策略 |

## 子账号方案的限制

子账号可以将员工日常操作账号和采集账号拆开，理论上能缓解同账号多设备互踢。但现场讨论发现，部分平台/店铺子账号可能需要新手机号注册和长期保号。按 200 个店铺估算，手机号月租可能达到每月数千元，客户未必接受。

因此子账号不能作为唯一方案。后续方案比较必须同时评估：

- 是否需要新增手机号；
- 新增手机号数量；
- 每月固定成本；
- 子账号权限是否覆盖所需数据；
- 子账号是否能授权第三方应用或 API；
- 客户是否愿意长期维护这些账号。

## 推荐验证实验

选择 5 到 10 个 Temu 店铺，连续 7 天记录以下信息：

| 字段 | 说明 |
|---|---|
| platform | 平台 |
| shop_name | 店铺 |
| account_type | 主账号/子账号 |
| employee_device | 员工设备 |
| collector_device | 采集设备 |
| login_action_time | 登录动作时间 |
| kicked_other_device | 是否顶掉另一设备 |
| verification_required | 是否要求验证码 |
| verification_type | 短信/邮箱/滑块/二次验证/无 |
| relogin_required | 次日采集是否需要重新登录 |
| risk_notice | 是否出现风控提示 |
| notes | 备注 |

验证目标：

- 判断已信任的两台设备来回顶号时，是否仍频繁触发验证码；
- 估算每天异常账号比例；
- 判断集中浏览器采集是否仍可作为兜底方案；
- 为 API、分布式采集或报表方案提供取舍依据。

## 方案方向调整

当前建议将“集中登录 200 个店铺账号”降级为兜底方案，优先研究以下路径：

1. 官方 API 或开放平台授权。
2. 客户已有 ERP、聚水潭、WMS、财务或物流系统的数据接口。
3. 平台后台的自动报表、导出历史、邮件报表。
4. 登录态在哪里，采集就在哪里发生的分布式员工电脑采集方案。
5. 手动导出文件 + 自动解析入库的低风险过渡方案。

## 决策记录

- 不做验证码绕过、接码平台、代理池、伪造设备指纹等高风险功能。
- 不采集或存储账号密码、cookie、token、验证码。
- 原始业务数据和客户报表文件不得未经确认离开客户授权范围。
- API 和子账号都不可行时，重点转向分布式采集、报表文件入口和现有 ERP 数据源。
