# 第一阶段驻场执行手册

## 总原则

1. 先观察完整人工流程，再写平台适配器。
2. 获取路径按风险从低到高选择：官方 API、官方导出、被动响应观察、DOM、低频内部请求、人工导出自动处理。
3. 多个平台可并行调查和开发，不等待单个平台完成 7 天观察。
4. 每个平台至少验证两个店铺；Temu 商品链接验证两个店铺、每店至少两个链接。
5. 每次采集均保留原始文件、时间、哈希和任务检查点。
6. 一个账号登录失效，只暂停该账号相关任务。
7. 未签字确认的数据口径不得进入正式经营汇总。

## 到场第 1 天：环境与人工流程

### 上午

- 记录 Windows、磁盘、安全软件、比特浏览器和 Local API 状态。
- 按[《比特浏览器配置与账号分配操作指南》](./bitbrowser-configuration-guide.md)完成 VPN 分流、测试窗口和指纹设置。
- 安装公共底座，验证 `/health` 和管理端。
- 填写账号、店铺、比特浏览器环境清单。
- 明确验证码和登录恢复责任人。

### 下午

- 财务负责人演示每个平台完整日报导出。
- Temu 运营演示过去 30 天上新产品、链接 ID 获取和批量查询。
- 每个数据集填写一份人工流程记录。
- 保存截图、录屏和样例报表到客户本地 evidence。
- 初选每个平台两个测试店铺。

## 到场第 2 天：技术探测与范围冻结

- 核验官方 API、授权、费用、字段和限流。
- 验证固定比特浏览器环境的打开、CDP 连接和登录持久化。
- 按最低风险路径探测数据获取方式。
- 记录验证码、风控、最大日期范围、分页和批量 ID 限制。
- 与数据负责人冻结第一阶段字段、筛选、时区、币种和总计口径。
- 为已冻结的平台分别建立适配器实施计划。

## 第 3 天起：并行开发与验证

各平台以独立工作流推进：

1. 店铺 A 跑通登录探测和原始报表归档。
2. 店铺 A 完成解析、校验、入库和人工对账。
3. 店铺 B 复用同一适配器，验证多店铺能力。
4. 同时启动其他已冻结平台的开发，不等待观察期结束。
5. Temu 财务与商品链接两条链路优先进入第一批。
6. 每个平台完成后立即进入连续两天定时观察。
7. 观察期间继续开发其他平台。

## 每个平台验收动作

- [ ] 两个店铺均自动获得目标数据。
- [ ] 原始报表和文件哈希存在。
- [ ] 必填列、空报表、重复键和总计校验有效。
- [ ] 自动结果与人工结果逐指标完全一致。
- [ ] 连续两天定时采集成功。
- [ ] 完成一次手动启动采集。
- [ ] 登录失效时仅相关账号进入 `waiting_auth`。
- [ ] 人工导出上传兜底可用。
- [ ] 填写平台验证评分卡。

## Temu 商品链接专项

- 两个 Temu 店铺。
- 每店至少两个商品链接 ID。
- 记录 ID 来源、批量提交入口、单批上限和查询窗口。
- 明确曝光、点击率、加购率、转化率、GMV 的字段与计算口径。
- 明确无数据链接、下架链接和重复链接的处理规则。
- 验证输出能够按店铺、链接和业务日期幂等更新。

## 每日收尾

- 更新问题清单、风险登记和第二天计划。
- 执行本地备份并检查备份文件。
- 将当日口径变化交负责人确认。
- 不将客户原始数据带离客户电脑。
- 记录已完成平台、观察中平台和可并行启动的平台。

## 第一阶段结束条件

- 需求一：目标平台各至少两个店铺完成最小闭环。
- 需求二：Temu 至少两个店铺、每店至少两个链接完成最小闭环。
- 连续两天定时成功并完成一次手动采集。
- 财务和运营负责人完成逐指标对账确认。
- 输出第一阶段可行性报告、第二阶段范围和估算依据。
- 若 3 至 5 天不足，按已确认机制延长驻场，不以牺牲准确性结束验证。
