# 分布式采集插件/客户端风险登记

日期：2026-06-16

## 背景

如果集中采集电脑登录 200 个店铺账号会导致员工账号被顶下线，而 API 和子账号方案又无法完全满足字段或成本要求，则可以采用“登录态在哪里，采集就在哪里发生”的分布式采集方案。

候选形态包括：

- 浏览器插件；
- 本地桌面采集客户端；
- 浏览器插件 + 本地客户端组合；
- 员工点击式半自动采集；
- 本地文件监听 + 中心解析。

## 风险总览

| 编号 | 风险 | 影响 | 概率 | 推荐控制 |
|---|---|---|---|---|
| R-001 | 员工电脑关机、休眠或断网 | 当日任务无法按时完成 | 高 | 中心记录设备在线状态，允许补采和超时提醒 |
| R-002 | 插件被员工卸载或浏览器禁用 | 页面数据无法采集 | 中 | 设备绑定和健康检查；企业策略或安装包管理 |
| R-003 | 客户端被杀毒软件拦截 | 采集程序无法运行 | 中 | 代码签名、安装说明、白名单流程 |
| R-004 | 自动化干扰员工正在操作的页面 | 影响日常工作 | 中 | 默认使用独立浏览器 profile 或后台窗口；支持员工确认后执行 |
| R-005 | 平台页面改版 | DOM 采集失效 | 高 | 优先接口响应/报表文件；页面解析加版本识别和失败截图 |
| R-006 | CSV/Excel 报表格式变化 | 解析失败或字段错位 | 高 | 中心解析器做表头校验、版本识别和异常隔离 |
| R-007 | 插件和客户端版本不一致 | 任务执行失败 | 中 | 自动更新、版本兼容策略、中心最低版本检查 |
| R-008 | 采集到敏感凭证 | 安全和合规风险 | 中 | 禁止采集 cookie、token、密码、验证码；字段白名单 |
| R-009 | 原始报表包含客户敏感数据 | GitHub 或外部系统泄露风险 | 高 | 原始文件留在授权存储；脱敏后再提交样例 |
| R-010 | 多设备数据重复上传 | 结果重复入库 | 中 | 文件 hash、业务主键、任务幂等键去重 |
| R-011 | 分布式故障定位困难 | 运维成本上升 | 中 | 客户端日志、截图、任务事件流和统一后台 |
| R-012 | 平台检测异常插件或自动化 | 账号风控 | 低到中 | 避免绕过风控；优先人工触发和报表导出；逐平台小规模试点 |

## 浏览器插件方案

### 适合场景

- 员工日常会打开平台后台页面；
- 数据直接展示在页面上；
- 页面底层接口返回结构化 JSON；
- 不需要复杂本地文件处理。

### 主要问题

- 插件依赖浏览器类型和版本，Chrome、Edge、比特浏览器等需要逐一验证。
- 浏览器关闭后，插件不能稳定承担后台定时任务。
- 插件处理本地下载文件、重命名、上传和断点续传的能力弱。
- DOM 解析对页面改版敏感。
- 如果监听接口响应，必须限制在业务数据白名单，不能采集凭证和无关流量。
- 插件分发、升级、权限声明和员工误删都需要管理机制。

### 控制措施

- 插件只负责页面内数据提取、接口响应解析、导出按钮触发。
- 插件不保存账号密码、cookie、token。
- 插件所有输出必须标注平台、页面 URL、店铺、任务 ID、采集时间和字段版本。
- 对页面 DOM 抓取添加表头/字段校验，失败时返回截图和错误类型。

## 本地客户端方案

### 适合场景

- 需要监听下载目录；
- 需要上传 CSV/Excel；
- 需要定时任务、重试、日志、截图、异常提醒；
- 需要复用已有 Playwright/Selenium/RPA 采集逻辑。

### 主要问题

- 需要在员工电脑安装程序，可能遇到 IT 权限、杀毒软件和系统策略限制。
- 员工电脑不一定每天在线。
- 自动控制浏览器可能干扰员工当前工作。
- 不同电脑的下载目录、浏览器 profile、屏幕分辨率、系统语言和文件权限存在差异。
- 需要远程排障和自动更新机制。

### 控制措施

- 客户端优先做任务调度、文件监听、上传和日志，不直接读取凭证。
- 自动化操作默认在独立 profile 或员工确认的窗口内执行。
- 上传原始文件前生成 hash，上传后等待中心确认。
- 本地失败保留任务日志、截图、文件路径和错误码。
- 中心后台展示设备在线状态、客户端版本、最近心跳和任务成功率。

## 插件 + 客户端组合方案

### 适合场景

- 同时存在页面可见数据和 CSV/Excel 导出数据；
- 需要页面内提取能力，也需要本地文件处理能力；
- 需要长期规模化支持 200 个店铺。

### 主要问题

- 系统复杂度最高，需要维护插件、客户端、中心服务和管理后台。
- 插件与客户端通信协议需要设计，故障链路变长。
- 首次部署步骤更多：安装客户端、安装插件、绑定员工、绑定设备、绑定店铺。
- 双端升级和兼容性必须纳入产品能力。

### 控制措施

- 插件负责“看网页”：页面 DOM、接口响应、导出触发。
- 客户端负责“管本地”：任务拉取、下载目录监听、文件上传、日志、截图、自动更新。
- 中心服务负责“做判断”：任务调度、字段映射、文件解析、去重、入库、监控。
- 插件和客户端之间只传任务 ID、页面业务数据、文件路径或下载事件，不传账号凭证。

## 推荐试点范围

第一阶段建议选择：

- 5 到 10 台员工电脑；
- 10 到 20 个店铺；
- Temu、TikTok Shop、SHEIN 各至少 2 个店铺；
- 聚水潭和京东各选择一个报表或接口场景；
- 连续运行 7 天。

试点验收指标：

- 不触发集中登录导致的员工账号互踢；
- 每日任务成功率达到可接受阈值；
- 文件上传可追溯，重复上传可去重；
- 页面或报表格式变化可被识别，不产生静默错误；
- 员工每日额外操作时间可量化；
- 客户能接受部署和维护方式。

## 安全边界

- 不绕过验证码。
- 不使用接码平台。
- 不伪造设备指纹或规避平台风控。
- 不采集密码、cookie、token、验证码。
- 不将客户原始经营数据提交到公共仓库。
- 所有原始文件和截图按客户授权范围保存、传输和删除。
