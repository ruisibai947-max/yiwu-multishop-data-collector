# 第二阶段：生产化扩展与整体交付实施计划

> **执行要求：** 实施时使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans`，按照任务和复选框逐项执行。第二阶段必须建立在第一阶段已确认的平台适配器、数据口径和实测结果之上。

**目标：** 把第一阶段公共底座和已验证适配器扩展到全部冻结店铺；多平台开发、等待和7天观察交叉并行；完成正式数据发布、运维能力、客户培训和完整源码交付。

**架构原则：**

- 调度、存储、校验、通知、本地管理和发布是公共能力。
- 五个平台仅开发各自独立适配器和字段映射。
- 不等待前一平台完成7天观察后才开始下一平台。
- 平台开发、账号等待、异步导出和稳定性观察可以重叠。
- SQLite是否迁移PostgreSQL必须由实测决定。

---

## 一个月目标节奏

一个月是目标，不是全部平台无条件完成的承诺：

- **第1～5天：** 冻结生产清单，补齐公共生产控制，启动高价值平台工作流。
- **第6～15天：** 分批扩展店铺；等待导出、验证或观察时开发其他平台。
- **第16～25天：** 多个平台7天观察重叠进行，处理失败并完成发布字段映射。
- **第26～30天：** 完成已满足观察期的平台验收，验证备份恢复，培训管理员并准备源码交付。

权限未提供、风控未解决、付费API未批准或冻结后新增范围的平台进入下一里程碑，不阻塞已经完成的平台。

## 任务7：多平台并行扩展到全部店铺

- [ ] **步骤1：采用交叉并行工作方式**

同一时段可以出现：

- 平台A正在写代码
- 平台B等待人工验证
- 平台C等待异步报表生成
- 平台D、E正在7天观察

不能因为某个平台等待而闲置。

- [ ] **步骤2：每个平台分批扩展**

1. 第一阶段2家测试店
2. 覆盖其他账号、站点和报表版本的小批次
3. 剩余冻结店铺
4. 实测后再提高并发

- [ ] **步骤3：每种差异都要人工对账**

至少覆盖每一种：

- 账号结构
- 站点和币种
- 报表版本
- 数据获取路径

不要求对完全同质的每家店永久逐项手工核对，但所有店持续执行自动完整性和合计校验。

- [ ] **步骤4：平台启用后立即进入观察**

多个平台的7天观察期可以重叠。

## 任务9：评估SQLite是否继续使用

**创建文件：**

- `customer-local-deliverables/database-capacity-assessment.md`

- [ ] **步骤1：测量SQLite**

记录：

- 数据库大小
- 每日新增行数
- 最大同时写入数
- 锁等待次数
- 最慢管理查询
- 备份耗时

- [ ] **步骤2：满足以下条件继续SQLite**

- 只有一台采集机
- 写入串行或低并发
- 没有反复锁失败
- 查询和备份满足时间要求

- [ ] **步骤3：出现实测触发条件才规划PostgreSQL**

触发条件：

- 多台采集机
- 反复写锁冲突
- 多个管理客户端并发使用
- 数据库操作超过约定窗口

不得为了“以后可能需要”而提前增加PostgreSQL复杂度。
