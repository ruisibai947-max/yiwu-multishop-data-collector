# 义乌跨境多店铺经营数据自动化技术方案

## 1. 文档目的

本文定义 Temu、Shein、TikTok Shop、京东、聚水潭多店铺经营数据自动化项目的技术边界、两阶段实施方案、数据架构、验收标准和驻场执行要求。

本文只包含技术方案和驻场执行清单，不包含报价、付款节点和合同模板。第一阶段现场确认并冻结的《平台－报表－字段－口径清单》是后续开发和验收的直接依据。

## 2. 项目背景

客户为义乌跨境电商团队，年营收约 10 亿元，团队约 200 人，其中财务人员 9 人。当前财务人员需要人工登录多个平台、多个店铺后台，导出数据并进行整理汇总。

客户需要解决两个问题：

### 2.1 需求一：多平台财务经营数据自动化

覆盖平台：

- Temu：约五六十家店铺
- Shein：几十家店铺
- TikTok Shop：几十家店铺
- 京东：几十家店铺
- 聚水潭：多店铺

候选数据包括 GMV、投流费用、退款及其他财务经营指标。最终字段、报表来源和口径在驻场后由财务负责人确认。

系统需要替代逐店手工导出和汇总，使老板、财务和运营能够每天查看公司、平台、店铺及原始明细层级的经营结果。

### 2.2 需求二：Temu 商品链接经营分析

系统根据商品链接 ID 获取商品表现，候选指标包括：

- 曝光
- 点击率
- 加购率
- 转化率
- GMV
- 现场确认的其他商品或广告指标

系统同时支持：

- 每天自动跟踪 Temu「商品分析」中“过去 30 天上新产品”；该入口和名称需在现场验证。
- 运营人员手工输入一批商品链接 ID 并立即查询。

是否细化至 SKU、是否关联 Temu 广告数据及 ROAS，由运营负责人在驻场后确认。

## 3. 已确认的项目原则

### 3.1 运行和数据安全

- 使用一台长期在线的专用 Windows 电脑作为主要采集主机。
- 客户允许安装开发和运行环境，并允许长期远程访问。
- 客户电脑可以访问 Codex、GitHub、npm 和 Python 包源。
- 客户已同意使用 Codex，但密码、Cookie、验证码和完整财务数据不得直接提交给模型。
- 账号凭证、Cookie、原始报表和真实经营数据不得离开客户电脑。
- 登录凭证和浏览器会话只保存在客户 Windows 电脑。
- 原始数据在本地保留一份。
- 是否将原始数据或汇总数据上传飞书、云数据库或自建系统，由驻场确认。

### 3.2 自动化等级

第一阶段目标为：

- 首次登录由人工完成。
- 后续每天定时自动采集一次。
- 管理员可随时手动启动采集。
- 登录失效、验证码或设备验证由人工处理。

每个平台按以下等级记录实际能力：

1. 全自动采集。
2. 自动执行到验证环节，人工验证后续跑。
3. 人工导出原始报表，系统自动监测、解析、汇总和发布。
4. 记录为当前无法安全自动化，并说明阻塞原因。

系统不开发验证码绕过、伪造指纹、代理轮换或突破平台限制的功能。

### 3.3 开发和交付

- 第一阶段预计驻场 3～5 个工作日，无法完成时允许延长驻场。
- 离场后可通过远程连接继续第一阶段开发和稳定性验证。
- 第二阶段由一人借助 Codex 开发。
- 第二阶段以一个月为目标期限，不作为全部平台无条件完成的硬性承诺。
- 第二阶段按平台分批上线，高价值平台优先，Temu 两项需求大概率进入第一批。
- 第一版范围冻结后，新增报表、字段、指标、平台或展示要求需重新评估。
- 需求一由一名财务负责人统一确认口径和验收。
- 需求二由一名 Temu 运营负责人统一确认口径和验收。
- 老板负责范围、优先级和付费 API 等决策。
- 最终交付可运行系统、完整项目源代码、部署文档和操作手册。

## 4. 技术路线

采用“分层混合采集”方案，不预设所有平台均无官方 API。

每个平台按以下优先级选择数据获取方式：

1. 免费且满足需求的官方 API。
2. 需要付费的官方 API，核算费用并由老板确认后使用。
3. 使用浏览器自动点击后台官方导出功能，下载 Excel 或 CSV 报表。
4. 监听页面正常加载时已经产生的网络响应，提取 JSON 数据。
5. 在风险、频率和平台规则评估后，低频复用后台内部请求。
6. 人工导出原始报表，系统自动处理，作为降级兜底。

财务数据优先使用官方 API 或官方报表，因为其最容易与人工口径完全对齐。商品链接数据若不能导出，再优先监听页面已有响应。主动复用非公开后台请求不是官方 API，可能发生限流、鉴权或结构变化，只能作为经过评估的补充方式。

## 5. 浏览器和多账号设计

### 5.1 比特浏览器优先

比特浏览器作为首选浏览器运行环境。系统通过比特浏览器 Local API 启动指定环境，再由 Playwright 通过调试地址接管浏览器，完成页面操作、筛选、下载和数据读取。

系统保留普通 Chrome 或 Edge 独立用户目录的兼容能力，作为部分平台与比特浏览器不兼容时的兜底。

### 5.2 隔离单位

真正的隔离单位是“独立登录账号对应的比特浏览器环境”，不是同一环境中的标签页。

映射关系如下：

```text
登录账号 A -> 比特环境 A -> 账号 A 可切换的一个或多个店铺
登录账号 B -> 比特环境 B -> 账号 B 可切换的一个或多个店铺
```

同一比特环境内的标签页会共享 Cookie 和登录状态，因此不能使用同一环境的不同标签页隔离两个独立账号。

### 5.3 运行方式

- 每个登录账号绑定一个固定的比特环境 ID。
- 账号能管理多个店铺时，在同一环境内依次切换店铺。
- 默认串行或低并发运行，不一次打开几十个浏览器环境。
- 任务完成后可以关闭环境释放资源；再次打开相同环境时复用已有会话。
- 第一阶段记录单账号、单店铺耗时和安全并发数，再评估一台采集主机是否足够。
- 员工正常运营不应被自动化影响；是否允许同一账号被员工和程序同时操作，现场实测后决定。必要时夜间或错峰运行。
- 无法安全迁移到专用电脑的账号，可以接入现有 Chrome、Edge 或支持 Local API/CDP 的指纹浏览器环境。

## 6. 总体系统架构

系统由六部分组成：

### 6.1 平台适配器

Temu、Shein、TikTok Shop、京东、聚水潭分别拥有独立适配器。

每个适配器负责：

- 登录状态检测
- 店铺切换
- 日期和筛选条件设置
- API、报表下载、页面响应监听或人工文件入口
- 平台原始字段解析
- 验证码、超时、页面变化等平台特有异常识别

所有适配器对公共系统提供统一任务接口，例如：

```text
采集指定账号下的指定店铺、数据类型和日期范围
```

一个平台改版时只修改该平台适配器，不影响其他平台、数据库和展示出口。

### 6.2 任务调度

任务调度负责：

- 每日固定时间创建自动任务
- 管理员手动创建立即采集或补采任务
- 串行或低并发安排账号和店铺
- 保存任务步骤和安全检查点
- 限制重试次数
- 单账号暂停和恢复
- 记录耗时、结果和失败原因

日期范围不在设计阶段写死。驻场后根据老板查看需求、财务核算习惯和平台数据延迟确定默认规则，同时保留可配置日期范围。

### 6.3 原始数据留档

每次采集先保留原始证据，再进行解析。

原始数据包括：

- 官方 Excel 或 CSV 报表
- 页面正常返回的 JSON
- 关键成功节点或异常截图
- 查询条件和时间信息
- 文件哈希

文件哈希使用 SHA-256 等算法根据文件内容生成，用于识别重复文件、发现原始文件变化和证明当时实际解析的是哪份文件。

关键时间至少包括：

- 任务开始和结束时间
- 平台查询的业务日期范围
- 报表生成和下载时间
- 解析入库时间
- 发布飞书时间

截图只保存账号和店铺确认、筛选条件、导出成功、页面合计或异常现场等关键节点，不对每一步截图。

### 6.4 标准化和校验

数据依次经过：

```text
原始文件或响应
-> 平台字段解析
-> 平台内标准化
-> 跨平台公共指标映射
-> 完整性和金额校验
-> 本地数据库
-> 汇总
-> 飞书或其他目标系统
```

同一平台不同店铺、站点或报表版本先在平台标准层统一。只有财务负责人确认含义一致的指标才进入跨平台汇总，不能仅因字段名称相同就直接相加。

### 6.5 本地数据库

第一阶段默认使用 SQLite。它无需单独运行数据库服务，便于在专用 Windows 电脑部署和备份。若第一阶段证明数据量、并发或访问方式超过 SQLite 能力，第二阶段迁移到 PostgreSQL。

本地数据库作为采集系统底账，保存：

- 平台、登录账号、店铺及比特环境绑定
- 定时任务和手动任务
- 每个任务步骤、状态、错误和重试次数
- 原始文件路径、哈希和解析状态
- 标准化财务经营数据
- Temu 商品链接日指标
- 汇总数据
- 发布飞书的状态和结果

账号密码和 Cookie 不以明文存入普通数据库。密码如需保存，使用 Windows 凭据管理器或经过评估的本地加密存储；Cookie 优先保留在对应浏览器环境中。

本地数据库支持：

- 防止重复采集导致数据翻倍
- 精确识别漏采店铺和日期
- 失败后只重试失败步骤
- 飞书失败后只重新发布，不重新登录平台采集
- 展示方式变化后重新生成输出，而无需重新采集

### 6.6 两个用户出口

本地管理端面向客户管理员和开发维护人员，负责采集运维：

- 平台、账号和店铺管理
- 比特环境绑定
- 新增、停用和修改店铺配置
- 定时任务配置
- 手动启动和指定日期补采
- 任务进度、成功和失败状态
- 登录失效等待处理
- 错误截图和日志
- 失败重试
- 原始文件查看
- 数据结果预览
- 飞书发布状态

本地管理端不是老板日常查看经营情况的正式看板。

经营数据出口面向老板、财务和运营：

- 优先写入飞书多维表格。
- 如果驻场后确认使用自建系统或其他数据库，只替换发布适配器，不重写采集流程。
- 支持公司总览、平台、店铺和原始明细逐层下钻。
- Temu 商品分析按店铺、链接 ID 和日期展示。

## 7. 数据分层设计

### 7.1 原始数据层

保留平台原始文件、原始响应、原始字段名称和原始值，不做覆盖性修改，用于审计、重新解析和定位差异。

### 7.2 平台标准层

每个平台建立自己的标准表和字段映射，例如：

- Temu 财务经营标准数据
- Temu 商品链接日指标
- Shein 财务经营标准数据
- TikTok Shop 财务经营标准数据
- 京东财务经营标准数据
- 聚水潭业务标准数据

Temu 商品链接日指标至少预留：

```text
业务日期、平台、站点、账号、店铺、商品链接 ID、
曝光、点击或点击率、加购或加购率、转化或转化率、
GMV、币种、采集批次、原始文件或响应引用
```

实际字段和数据粒度由现场报表确认。

### 7.3 跨平台汇总层

候选公共维度：

- 业务日期
- 平台
- 站点
- 登录账号
- 店铺
- 原币种

候选公共指标：

- GMV
- 退款金额
- 投流费用
- 订单数
- 销售件数

币种换算方式、汇率来源和汇率日期由财务负责人现场确认。系统始终保留原始币种和原始金额。

## 8. 单次采集任务流程

定时采集和手动采集使用同一流程：

1. 创建任务，记录平台、账号、店铺、数据类型、日期范围和触发来源。
2. 通过比特 Local API 打开该账号绑定的浏览器环境。
3. 检查登录状态和当前账号、店铺身份。
4. 按该平台适配器执行 API、报表下载、页面响应监听或人工文件接收。
5. 保存原始文件、响应、关键截图、筛选条件和时间。
6. 解析并转换成平台标准数据。
7. 检查字段结构、空数据、记录数、合计、重复和必填值。
8. 幂等写入本地数据库。
9. 生成店铺、平台和公司汇总。
10. 发布到飞书或现场确认的目标系统。
11. 记录任务结果、耗时、自动化等级和发布状态。

## 9. 幂等去重和断点重试

### 9.1 幂等去重

相同业务数据重复采集时，数据库最终只保留一份有效结果，不重复累计。

业务唯一标识根据数据粒度定义，例如：

```text
平台 + 店铺 ID + 业务日期 + 报表类型 + 平台业务记录 ID
```

处理规则：

- 不存在时新增。
- 已存在且内容相同时跳过。
- 已存在但平台数据发生更新时更新有效记录，并保留处理记录。

### 9.2 断点重试

任务按安全检查点记录状态，失败后从合适步骤恢复，而不是盲目从页面某个点击位置继续。

安全检查点包括：

- 单账号
- 单店铺
- 单张报表
- 原始文件下载
- 解析
- 入库
- 发布

例如飞书发布失败时直接重试发布，不重新登录平台；账号下前六家店成功、第七家失败时，从第七家恢复，不重新采集前六家。

## 10. 登录失效和任务暂停

系统采用“两层检测、局部暂停”。

任务开始前：

- 打开当前账号环境。
- 检查登录是否有效。
- 无效时将该账号任务标记为等待人工处理。
- 继续运行其他独立账号和平台。

任务执行中：

- 检测到登录页、验证码或设备验证时，暂停当前账号及其关联店铺。
- 保存当前步骤和错误截图。
- 在本地管理端显示，并发送飞书通知。
- 其他独立账号和平台继续运行。

人工完成验证后，系统重新检查登录状态，从安全检查点重试。

只有出现平台级系统性风险、多个账号连续出现相同封控、平台整体改版或管理员主动操作时，才暂停整个平台或全部系统。

## 11. 异常处理

### 11.1 登录与风控

- 暂停当前账号。
- 不自动绕过验证码。
- 不无限重试。
- 保存截图并通知管理员。

### 11.2 页面或报表变化

- 按钮、字段或文件结构不符合预期时，停止对应数据源入库。
- 原始文件仍保留。
- 将数据标记为待适配，避免字段错位污染正式汇总。

### 11.3 平台和网络故障

- 对超时、服务器错误和异步导出未完成采用有限次数的退避重试。
- 超过阈值后标记失败并通知，等待后续补采。

### 11.4 空数据

空数据可能代表正常零业务，也可能代表筛选错误、权限不足或页面未加载。

系统结合页面状态、原始文件、历史数据和必要字段判断。无法确认时不发布到正式汇总。

### 11.5 数据校验失败

字段缺失、合计不一致或重复异常的数据进入隔离状态，不参与正式汇总和飞书发布。

### 11.6 飞书发布失败

本地采集和入库仍保持成功状态。系统只重试发布，不重新采集平台数据。

## 12. 数据准确性

第一阶段必须在以下条件完全相同时，与人工导出结果逐项一致：

- 店铺
- 日期范围
- 时区
- 币种
- 筛选条件
- 平台数据更新时间

发现不一致时必须定位原因并记录，不能仅以“已经抓到数据”作为通过。

生产运行的数据准确性闸门为：

1. 原始文件或响应存在且可读取。
2. 字段结构符合冻结版本。
3. 必填字段、记录数和金额合计通过校验。
4. 幂等入库成功。
5. 数据才允许进入汇总和发布。

异常波动只告警，不由系统擅自修改经营数据。

## 13. 第一阶段：最小闭环验证

### 13.1 验证范围

需求一：

- Temu、Shein、TikTok Shop、京东、聚水潭每个平台至少 2 家真实店铺。
- 两家店铺尽量覆盖不同登录方式、站点或后台差异。
- 驻场盘点全部报表后，由财务负责人指定每个平台最小字段集。

需求二：

- Temu 至少 2 家店铺。
- 每家至少 2 个商品链接。
- 验证每日自动获取“过去 30 天上新产品”清单。
- 验证运营手工输入商品链接 ID 的立即查询入口。
- 第一阶段最低验证到商品链接 ID 级；SKU 级由现场确认。

第一阶段不回填部署前的历史财务经营数据，只验证部署后的每日新增采集。Temu“过去 30 天上新产品”是需求二在当前查询时点使用的平台商品清单或统计窗口，不视为历史数据回填；系统只保存验证期间实际取得的每日结果。

### 13.2 驻场安排

第 1 天：

- 建立平台、站点、账号、店铺、登录方式和比特环境组成的账号地图。
- 财务和 Temu 运营逐步演示当前人工流程。
- 保存原始报表样例和现有最终汇总表。
- 记录页面入口、筛选条件、日期、币种、导出步骤和一次查询限制。
- 每个平台选择 2 家具有代表性差异的真实测试店铺。

第 2 天：

- 建立并确认《平台－报表－字段－口径清单》。
- 确认后台类型、国家站点、时区、币种和数据延迟。
- 检查官方 API、权限范围、费用和字段覆盖度。
- 验证比特 Local API、Playwright 接管、下载和会话复用。
- 记录验证码、设备绑定、员工并发操作和平台风控情况。

第 3～5 天：

- 优先打通 Temu 财务数据和商品链接数据。
- 推进其他平台各 2 家店铺的最小数据闭环。
- 建立原始留档、解析、校验、本地数据库和轻量管理页。
- 对无法安全全自动的平台验证降级方式。

驻场后或延长驻场：

- 完成连续 2 天定时采集。
- 验证至少 1 次手动采集。
- 完成人工逐项对账。
- 验证失败通知、局部暂停、重试和补采。

### 13.3 第一阶段通过标准

需求一：

- 五个平台分别至少 2 家店铺。
- 完成最小字段集的自动获取或已确认的降级自动化。
- 完成原始留档、标准化、入库、汇总和本地展示。
- 连续 2 天定时采集成功。
- 至少 1 次手动采集成功。
- 无重复入库和漏采。
- 与人工同条件结果完全一致。
- 记录各平台实际自动化等级和限制。

需求二：

- Temu 至少 2 家店铺，每家至少 2 个商品链接。
- 商品指标按业务日期保存并本地展示。
- 连续 2 天定时采集成功。
- 至少 1 次手工链接查询成功。
- 自动清单和手工清单入口均完成验证。
- 与运营人工同条件查询结果完全一致。

### 13.4 第一阶段交付

- 仅覆盖已验证测试店铺、可继续每日运行的验证程序。
- 轻量本地管理页。
- 《平台－报表－字段－口径清单》。
- 《账号－比特环境－店铺映射清单》。
- 《可行性验证报告》，包含各平台结果、自动化等级、准确性、耗时、风险和第二阶段工作量依据。
- 若现场确认最终使用飞书，增加最小飞书写入验证；否则本地闭环即为第一阶段展示验收。

第一阶段不代表全部店铺生产交付，也不证明上百家店铺规模下的性能和长期稳定性。

### 13.5 第一阶段验收证据

每个平台和需求需保留：

- 测试平台、账号、店铺、数据类型和日期范围。
- 实际采用的采集方式及自动化等级。
- 连续 2 天定时任务记录和 1 次手动任务记录。
- 原始文件或响应、关键截图、文件哈希和解析条数。
- 自动结果与人工结果的逐项对账记录。
- 失败、人工验证、重试或补采的验证记录。
- 单店耗时、单账号耗时、失败率和建议安全并发数。
- 未解决风险、降级方式和第二阶段处理建议。

## 14. 第二阶段：整体开发和交付

### 14.1 平台分批上线

第一阶段后依据业务价值、人工耗时和技术风险冻结顺序。Temu 两项需求大概率作为第一批。

每个平台独立完成：

1. 冻结报表、字段、口径、目标店铺和频率。
2. 从 2 家测试店扩展到全部目标店铺。
3. 覆盖不同站点、账号结构和报表版本并进行抽样对账。
4. 连续 7 天稳定运行。
5. 由对应负责人验收后进入日常运行。

各平台适配器可以并行推进，不需要等待前一个平台完成开发或连续 7 天稳定性观察后才开始下一个平台。已完成基本开发的平台立即进入 7 天稳定性观察；观察期间继续开发、调试其他平台。多个平台的稳定性观察期可以重叠。

由于项目由一人开发，“并行”是指工作流和等待周期并行，而不是同时编写多个平台代码：当某个平台处于定时运行、等待数据生成、等待人工验证或稳定性观察阶段时，开发者立即切换到其他平台推进，出现告警时再回到对应平台处理。

### 14.2 生产能力

第二阶段需补齐：

- 客户管理员可自行新增、停用和修改店铺。
- 账号、比特环境和店铺的可配置绑定。
- 任务队列、错峰运行和实测后的安全并发。
- 幂等去重、断点重试和指定日期补采。
- 登录失效局部暂停和人工恢复。
- 页面、字段和报表格式变化检测。
- 本地管理端任务看板。
- 飞书失败通知和发布重试。
- 原始文件、日志和数据库备份、归档及清理策略。
- 公司、平台、店铺和原始明细下钻展示。

### 14.3 平台级验收

每个平台上线需连续 7 天满足：

- 按时完成全部目标店铺采集。
- 无重复、漏采和错误归属。
- 金额和核心指标与人工结果一致。
- 登录失效、失败通知和人工恢复有效。
- 失败任务能够补采。
- 管理员可自行新增、停用和手动运行店铺。

### 14.4 工期顺延条件

以下情况需要重新评估平台顺序或工期：

- 冻结后新增平台、报表、字段、指标或展示要求。
- 客户无法及时提供账号、权限、验证码或负责人确认。
- 平台存在强制风控、设备绑定或长期不可用。
- 付费官方 API 或第三方服务未获批准。
- 一台采集主机经实测无法满足每日运行窗口。
- 平台页面、报表或鉴权机制发生重大变化。

## 15. 测试策略

### 15.1 解析测试

使用客户电脑内的真实样例和本地构造的脱敏样例，验证：

- 字段映射
- 日期和时区
- 金额和小数精度
- 空值和异常格式
- 新旧报表版本

### 15.2 任务测试

验证：

- 相同任务重复运行不产生重复数据
- 下载成功、解析失败后的恢复
- 入库成功、飞书失败后的发布重试
- 单账号失败时其他任务继续
- 人工验证后恢复
- 指定日期补采

### 15.3 现场端到端测试

使用真实账号、真实比特环境、真实店铺和真实报表完成端到端测试。

### 15.4 稳定性测试

- 第一阶段：连续 2 天定时成功并验证 1 次手动采集。
- 第二阶段：每个平台连续 7 天稳定运行。

## 16. 通知和可观测性

本地管理端展示：

- 平台、账号、店铺和报表当前状态
- 当前任务步骤和进度
- 最后成功采集时间
- 最后成功发布时间
- 耗时、重试次数和失败原因
- 等待人工验证的账号

飞书机器人通知至少包括：

- 平台
- 账号或店铺
- 失败时间
- 失败类别
- 管理员需要执行的动作

通知和日志不得包含密码、Cookie、验证码或完整敏感数据。

## 17. 驻场前置条件

客户需提供：

- 每个平台至少 2 家可正常登录的真实店铺。
- 财务、广告、退款、商品分析等必要权限。
- 一名财务负责人和一名 Temu 运营负责人全程配合。
- 短信、扫码、验证码或设备验证的及时协助。
- 一台允许安装软件、长期在线且可长期远程访问的 Windows 电脑。
- 客户对浏览器自动化、报表下载和后台网络请求分析的明确授权。
- 用于低风险验证的店铺，并约定出现风险提示后的停止条件。

所有人工流程和后台页面只能驻场后查看，因此首日以盘点和取证为主，不能预设直接进入批量开发。

## 18. 现场必须确认并冻结的事项

以下不是设计缺失，而是必须通过真实后台和负责人决策确定的现场输入：

- 各平台具体后台类型、国家站点、时区和币种。
- 登录账号与店铺的实际关系。
- 现有比特浏览器、其他指纹浏览器和员工电脑环境。
- 每个平台全部人工报表和最终汇总表。
- 第一阶段最小报表、字段和指标。
- 默认每日采集的日期范围。
- 平台数据延迟和财务核算时点。
- GMV、退款、投流费用等指标的业务定义。
- 币种换算、汇率来源和汇率日期。
- Temu 过去 30 天上新商品入口和商品链接批量查询流程。
- 商品链接级或 SKU 级粒度。
- 是否关联 Temu 广告数据及归因口径。
- 飞书多维表格或自建系统的最终展示方式。
- 原始文件和日志的保留期限。
- 员工与自动化是否可以同时操作同一账号。
- 专用 Windows 电脑的实际配置。
- 全部店铺完成一次日采集所需的时间窗口。

这些事项在《平台－报表－字段－口径清单》确认后冻结。未冻结事项不能作为开发完成前的隐含验收要求。

## 19. 推荐技术基线

在第一阶段现场验证未发现兼容性问题时，推荐：

- Node.js + TypeScript：任务服务和平台适配器
- Playwright：浏览器自动化和网络响应监听
- 比特浏览器 Local API：账号环境启动、关闭和隔离
- SQLite：第一阶段及初始生产底账
- 本地轻量 Web 管理页：店铺配置、任务运行和异常处理
- 飞书开放能力或机器人：数据发布和失败通知
- Windows 任务服务或常驻进程：每日定时运行

技术基线可因官方 API SDK、客户现有系统或现场兼容性调整，但数据分层、适配器边界、任务状态和验收标准保持不变。

## 20. 明确不在范围内

- 自动绕过验证码和平台风控。
- 自动更换指纹、代理轮换或隐藏违规自动化行为。
- 第一阶段回填部署前的历史财务经营数据。
- 第一阶段覆盖全部店铺。
- 未经财务负责人确认，擅自将同名指标跨平台相加。
- 将客户真实凭证和原始数据复制到开发者个人电脑。
- 在范围冻结后无条件增加新报表、字段或平台。
